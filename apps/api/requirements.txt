#
# Why this cluster moves together (the matgl-4 migration):
#   * matgl==4.0.2 — 1.1.3's auto-download URL is dead AND its checkpoint
#     format (dgl-era) can no longer deserialize the only weights still hosted
#     (the Hugging Face `materialyze` org publishes matgl's *current* pyg-era
#     format). matgl 4.x drops dgl for torch-geometric and loads those weights;
#     it requires pymatgen-core>=2026.5.18, which forces the rest of this bump.
#   * pymatgen==2026.5.4 (full) + pymatgen-core==2026.5.18 — in 2026.x pymatgen
#     split: the full meta-package (analysis/entries) layers on pymatgen-core.
#     Full pymatgen's latest is 2026.5.4 and it depends on pymatgen-core>=2026.4.16,
#     so pymatgen-core resolves to 2026.5.18 satisfying BOTH it and matgl. Pin
#     both exactly — they were verified as a pair.
#   * emmet-core==0.87.1 / mp-api==0.46.4 — the 2026.x-compatible pair
#     (emmet-core>=2024.6.10 pymatgen floor, mp-api>2024.2.20); the old
#     0.84.10/0.45.8 were pinned to pymatgen 2025.6.14.
#   * matminer==0.10.1 — required for pymatgen 2026.x compat; it pulls scipy
#     >=1.17 (hence the scipy bump below).
#   * h5py>=3.16 — earlier wheels were built against NumPy 1.x; their Cython
#     extensions raise "numpy.dtype size changed (96 vs 88)" at import time
#     when pymatgen.io.vasp.outputs pulls them in.
